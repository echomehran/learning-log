دستور `git bisect` یک ابزار جست‌وجوی دودویی در گیت است که به شما کمک می‌کند به‌جای بررسی دستی تمام کامیت‌ها، کامیت عامل یک باگ یا رگرسیون را با سرعت لگاریتمی پیدا کنید. در یک تاریخچه با هزار کامیت، تقریباً ده مرحله برای پیدا کردن مقصر کافی است .

### ۱. الگوریتم واقعی `git bisect`: چگونه بهترین کامیت را انتخاب می‌کند؟

برخلاف تصور رایج، `git bisect` فقط وسط یک بازه خطی را انتخاب نمی‌کند. تاریخچه گیت یک گراف جهت‌دار بدون دور (DAG) است که شامل شاخه‌ها و کامیت‌های ادغامی است. بنابراین گیت باید در هر مرحله «بهترین کامیت برای تقسیم» را پیدا کند.

گیت برای این کار به هر کامیت یک امتیاز می‌دهد که بر اساس تعداد اجداد آن محاسبه می‌شود. هدف این است که تابع زیر بیشینه شود :

```text
f(X) = min(تعداد اجداد X, تعداد کل کامیت‌ها - تعداد اجداد X)
```

این فرمول تضمین می‌کند که با علامت‌گذاری کامیت انتخاب‌شده، چه خوب و چه بد، بیشترین اطلاعات ممکن به دست می‌آید. اگر کامیت X «خوب» باشد، می‌دانیم همه اجداد آن هم خوب هستند. اگر «بد» باشد، می‌دانیم فقط اجداد آن می‌توانند مقصر باشند و بقیه گراف از دور خارج می‌شوند .

گیت برای سرعت بیشتر، اگر بتواند کامیتی با امتیاز `N/2` پیدا کند، فوراً جست‌وجو را متوقف می‌کند، چون هیچ کامیتی نمی‌تواند امتیاز بالاتری بگیرد .

### ۲. مکانیزم دقیق `git bisect run` و کدهای خروجی

وقتی از `git bisect run <script>` استفاده می‌کنید، گیت اسکریپت شما را روی هر کامیت اجرا می‌کند و بر اساس کد خروجی آن تصمیم می‌گیرد. قواعد دقیق کدهای خروجی به شرح زیر است :

- **کد خروجی `0`**: کامیت فعلی «خوب» است.
- **کدهای خروجی `1` تا `124` و `126` تا `127`**: کامیت فعلی «بد» است.
- **کد خروجی `125`**: این کامیت «غیرقابل آزمایش» است و باید رد شود (skip).

انتخاب عدد `125` تصادفی نیست. در پوسته‌های POSIX، کد `126` به معنای «فایل اجرایی نیست» و `127` به معنای «دستور پیدا نشد» است. بنابراین `125` بالاترین عددی است که می‌تواند به‌عنوان یک وضعیت «رد کردن» سفارشی استفاده شود بدون اینکه با خطاهای عادی پوسته تداخل کند .

### ۳. نکات عمیق درباره ادغام‌ها (Merge Commits) و محدودیت‌های `git bisect`

یکی از عمیق‌ترین نکات درباره `git bisect` این است که این دستور می‌تواند در برخورد با ادغام‌ها دچار مشکل شود. اگر یک باگ از طریق یک کامیت ادغام وارد شاخه اصلی شده باشد، `git bisect` ممکن است آن را به‌درستی پیدا نکند.

دلیل این محدودیت به نحوه عملکرد گیت در نمایش تغییرات ادغام‌ها برمی‌گردد. به‌طور پیش‌فرض، `git log` و دستورهایی که بر اساس آن کار می‌کنند، تغییرات یک کامیت ادغام را نسبت به فقط یکی از والدین آن (والد اول) نشان می‌دهند. اگر تغییری از والد دوم آمده باشد، ممکن است در این نمایش دیده نشود .

راه‌حل این مشکل استفاده از گزینه `--ancestry-path` همراه با `git rev-list` و محدود کردن `git bisect` به کامیت‌هایی است که از یک نقطه مشخص ارث‌بری می‌کنند. یک الگوی کاربردی برای این کار به شکل زیر است :

```bash
git bisect start $badCommit $goodCommit
git bisect run bash -c "! git merge-base --is-ancestor $goodCommit HEAD || git grep -q $TERM"
git bisect reset
```

در این دستور، شرط `! git merge-base --is-ancestor $goodCommit HEAD` بررسی می‌کند که آیا کامیت فعلی از `$goodCommit` ارث‌بری می‌کند یا خیر. اگر ارث‌بری نکند، آن را «خوب» علامت می‌زند تا گیت از بررسی شاخه‌های نامرتبط صرف‌نظر کند .

### ۴. رفتار گیت هنگام رد کردن کامیت‌ها (`git bisect skip`)

وقتی کامیتی را رد می‌کنید، الگوریتم `git bisect` تغییر می‌کند. گیت ابتدا لیست کامیت‌ها را بر اساس امتیاز نزولی مرتب می‌کند، سپس کامیت‌های رد‌شده را از لیست حذف می‌کند و در نهایت با استفاده از یک مولد اعداد شبه‌تصادفی (PRNG) یکی از کامیت‌های باقی‌مانده را انتخاب می‌کند .

این مکانیزم تصادفی به این دلیل است که گیت نمی‌داند کامیت‌های رد‌شده در کدام سمت «خوب/بد» قرار دارند. بنابراین انتخاب تصادفی از میان گزینه‌های معتبر، بهترین تخمین را ارائه می‌دهد. اما یک هشدار مهم وجود دارد: اگر کامیتی که رد می‌کنید دقیقاً مجاور کامیت مقصر باشد، گیت ممکن است نتواند با اطمینان بگوید کدام یک اولین کامیت بد بوده است .

### ۵. تکنیک‌های پیشرفته: استفاده از واژگان سفارشی

از نسخه‌های جدید گیت، می‌توانید به‌جای «خوب/بد» از واژگان دلخواه استفاده کنید. این ویژگی به‌ویژه هنگام جست‌وجوی رگرسیون عملکردی یا باگ‌هایی که با «خوب/بد» قابل توصیف نیستند، مفید است .

```bash
git bisect start --term-old fast --term-new slow
```

پس از این دستور، به‌جای `git bisect good` از `git bisect fast` و به‌جای `git bisect bad` از `git bisect slow` استفاده می‌کنید .

### ۶. اشکال‌زدایی و بازپخش جست‌وجو

اگر در علامت‌گذاری کامیت‌ها اشتباه کردید، می‌توانید از `git bisect log` برای ذخیره تاریخچه استفاده کنید. پس از ویرایش دستی فایل، با `git bisect replay <file>` جست‌وجو را از نو بازسازی کنید . همچنین برای دیدن کامیت‌های باقی‌مانده، `git bisect visualize` یا `git bisect view` در دسترس است که در محیط گرافیکی `gitk` را باز می‌کند .
