# فصل اول: مفهوم `git reset`

دستور `git reset` برای تغییر وضعیت فعلی Git استفاده می‌شود. این دستور می‌تواند محل اشارهٔ شاخهٔ فعلی را تغییر دهد، محتوای `staging area` را بازنشانی کند یا تغییرات فایل‌های موجود در `working tree` را نیز کنار بگذارد.

قدرت این دستور از آنجا ناشی می‌شود که می‌تواند روی چند بخش مختلف از مدل داده‌ای Git اثر بگذارد.

برای استفادهٔ حرفه‌ای از `git reset` باید سه سؤال را از هم جدا کنیم:

- آیا می‌خواهیم commit فعلی را از تاریخچهٔ شاخه کنار بگذاریم؟
- آیا می‌خواهیم فایل‌های `staged` را از حالت آمادهٔ commit خارج کنیم؟
- آیا می‌خواهیم تغییرات فایل‌های موجود در `working tree` را نیز حذف کنیم؟

پاسخ به این سؤال‌ها تعیین می‌کند که کدام حالت `reset` مناسب است.

## ۱.۱. یک مثال ساده

فرض کن تاریخچهٔ مخزن به این شکل است:

```text
A --- B --- C  (HEAD -> main)
```

در این وضعیت:

- `A`، `B` و `C` سه commit هستند.
- شاخهٔ `main` به commit شمارهٔ `C` اشاره می‌کند.
- عبارت `HEAD -> main` نشان می‌دهد که `HEAD` در حالت معمول به شاخهٔ فعلی اشاره می‌کند و آن شاخه نیز به commit `C` اشاره دارد.

حالا دستور زیر را اجرا می‌کنیم:

```bash
git reset --soft HEAD~1
```

تاریخچهٔ شاخه به شکل زیر درمی‌آید:

```text
A --- B  (HEAD -> main)
       \
        C
```

در این نمایش، `C` دیگر بخشی از تاریخچهٔ قابل‌دسترسی شاخهٔ `main` نیست؛ اما خود commit لزوماً بلافاصله حذف نشده است.

نکتهٔ مهم این است که `git reset` معمولاً commit جدیدی نمی‌سازد. این دستور محل اشارهٔ شاخهٔ فعلی را تغییر می‌دهد.

همچنین، نوع `reset` تعیین می‌کند که محتوای `staging area` و فایل‌های کاری چه وضعیتی پیدا کنند.

# فصل دوم: مدل ذهنی Git

برای درک دقیق `git reset` ابتدا باید اجزای اصلی وضعیت Git را بشناسیم.

## ۲.۱. سه بخش مهم

### الف) `HEAD`

عبارت `HEAD` مشخص می‌کند که Git در حال حاضر در چه نقطه‌ای از تاریخچه قرار دارد.

در حالت معمول، `HEAD` به شاخهٔ فعلی اشاره می‌کند و شاخه به یک commit اشاره دارد.

برای مشاهدهٔ مقدار `HEAD` می‌توانیم از این دستور استفاده کنیم:

```bash
git log -1 --oneline
```

برای دیدن commitای که `HEAD` مستقیماً به آن resolve می‌شود:

```bash
git rev-parse HEAD
```

### ب) `Index` یا `Staging Area`

بخش `index` جایی است که Git محتوای آمادهٔ commit بعدی را نگه می‌دارد.

وقتی دستور زیر را اجرا می‌کنیم:

```bash
git add app.py
```

محتوای فعلی فایل `app.py` به `staging area` اضافه می‌شود.

اگر بعد از آن فایل را دوباره ویرایش کنیم، ممکن است نسخهٔ موجود در `staging area` با نسخهٔ موجود در `working tree` متفاوت باشد.

### ج) `Working Tree`

این بخش شامل فایل‌هایی است که در دایرکتوری کاری مخزن می‌بینی.

وقتی فایلی را ویرایش می‌کنی، معمولاً ابتدا `working tree` تغییر می‌کند. این تغییر تا زمانی که آن را `stage` نکنی، لزوماً وارد `index` نمی‌شود.

## ۲.۲. تصویر ذهنی

مدل ساده‌شدهٔ Git را می‌توان این‌گونه در نظر گرفت:

```text
HEAD
 │
 ▼
Commit History

Index / Staging Area
 │
 ▼
Working Tree
```

این شکل صرفاً یک مدل مفهومی است؛ ارتباط واقعی این اجزا پیچیده‌تر است.

برای فهم `reset`، تفاوت میان این سه وضعیت مهم است:

- محتوای ثبت‌شده در commit فعلی
- محتوای آماده‌شده در `index`
- محتوای موجود در فایل‌های کاری

## ۲.۳. بررسی وضعیت قبل از `reset`

قبل از اجرای دستورهای حساس، وضعیت مخزن را بررسی کن:

```bash
git status
```

برای مشاهدهٔ تاریخچهٔ خلاصه:

```bash
git log --oneline --decorate -10
```

برای بررسی تفاوت فایل‌های کاری با `index`:

```bash
git diff
```

برای بررسی تفاوت `index` با آخرین commit:

```bash
git diff --cached
```

این چهار دستور به تو کمک می‌کنند قبل از تغییر وضعیت مخزن بفهمی دقیقاً چه چیزی در اختیار داری.

# فصل سوم: سه حالت اصلی `git reset`

سه حالت اصلی این دستور عبارت‌اند از:

```bash
git reset --soft <target>
git reset --mixed <target>
git reset --hard <target>
```

تفاوت این سه حالت در میزان بازنشانی وضعیت Git است.

## ۳.۱. حالت `soft`

در حالت `soft`، شاخهٔ فعلی به commit هدف منتقل می‌شود، اما `index` و `working tree` دست‌نخورده باقی می‌مانند.

ساختار دستور:

```bash
git reset --soft <target>
```

مثال:

```bash
git reset --soft HEAD~1
```

فرض کن قبل از اجرا، وضعیت به این شکل باشد:

```text
A --- B --- C  (HEAD -> main)
```

بعد از اجرا:

```text
A --- B  (HEAD -> main)
       \
        C
```

در این مثال، `HEAD` اکنون به `B` اشاره می‌کند؛ اما تغییراتی که در commit `C` ثبت شده بودند، در `index` باقی می‌مانند.

در نتیجه، اجرای دستور زیر می‌تواند تغییرات آمادهٔ commit را نشان دهد:

```bash
git diff --cached
```

### کاربردهای `soft`

این حالت زمانی مفید است که بخواهی:

- آخرین commit را باز کنی و محتوای آن را اصلاح کنی.
- چند commit کوچک را به یک commit تبدیل کنی.
- پیام commit را تغییر دهی.
- اصلاحیه: commit اشتباهی ساخته باشی، اما بخواهی تغییرات آن برای commit مجدد آماده بمانند.

### مثال: اصلاح آخرین commit

فرض کن آخرین commit را ساخته‌ای، اما متوجه شده‌ای که توضیح یا محتوای آن باید اصلاح شود.

```bash
git reset --soft HEAD~1
```

حالا تغییرات commit قبلی در `staging area` باقی می‌مانند.

پس از اصلاح فایل‌ها:

```bash
git add .
git commit -m "feat(parser): improve input validation"
```

در این روش، commit قبلی از نو ساخته می‌شود و شناسهٔ commit جدید خواهد بود.

نکته: اگر commit قبلی قبلاً به مخزن مشترک push شده باشد، بازنویسی تاریخچه می‌تواند برای همکاران مشکل ایجاد کند. پیش از انجام این کار، وضعیت شاخهٔ remote و همکاری تیمی را بررسی کن.

---

## ۳.۲. حالت `mixed`

حالت `mixed`، علاوه بر جابه‌جاکردن شاخه به commit هدف، `index` را نیز با محتوای آن commit هماهنگ می‌کند؛ اما فایل‌های موجود در `working tree` را بازنویسی نمی‌کند.

این حالت، رفتار پیش‌فرض `git reset` است.

بنابراین این دو دستور از نظر نوع reset معادل‌اند:

```bash
git reset --mixed HEAD~1
```

```bash
git reset HEAD~1
```

مثال:

```bash
git reset --mixed HEAD~1
```

پس از اجرای دستور:

- شاخه به commit قبلی منتقل می‌شود.
- تغییرات commit کنارگذاشته‌شده دیگر در `index` به‌صورت staged باقی نمی‌مانند.
- تغییرات معمولاً در `working tree` باقی می‌مانند و به‌صورت unstaged دیده می‌شوند.

برای بررسی وضعیت:

```bash
git status
```

برای مشاهدهٔ تفاوت فایل‌های کاری با `index`:

```bash
git diff
```

### کاربردهای `mixed`

این حالت برای مواقعی مناسب است که بخواهی:

- آخرین commit را باز کنی.
- فایل‌های آن را از حالت `staged` خارج کنی.
- تغییرات را نگه داری و بعداً تصمیم بگیری کدام فایل‌ها باید وارد commit شوند.
- یک commit اشتباهی را کنار بگذاری، بدون اینکه تغییرات معمول فایل‌های tracked را فوراً از `working tree` حذف کنی.

### مثال: بازگرداندن فایل‌ها به حالت unstaged

فرض کن سه فایل در آخرین commit ثبت شده‌اند:

```text
app.py
tests/test_app.py
README.md
```

حالا می‌خواهی commit را باز کنی و فقط دو فایل را دوباره stage کنی.

```bash
git reset --mixed HEAD~1
```

سپس:

```bash
git add app.py tests/test_app.py
git commit -m "feat(app): add input validation"
```

در این حالت، تغییرات `README.md` در فایل کاری باقی می‌مانند، اما وارد commit جدید نمی‌شوند؛ مگر اینکه بعداً آن‌ها را stage کنی.

---

## ۳.۳. حالت `hard`

حالت `hard` شاخهٔ فعلی را به commit هدف منتقل می‌کند، `index` را با آن commit هماهنگ می‌کند و فایل‌های tracked موجود در `working tree` را نیز با محتوای آن commit تطبیق می‌دهد.

ساختار دستور:

```bash
git reset --hard <target>
```

مثال:

```bash
git reset --hard HEAD~1
```

بعد از اجرا، وضعیت شاخه، `index` و فایل‌های tracked به وضعیت commit قبلی برمی‌گردد.

### هشدار مهم

دستور `git reset --hard` می‌تواند تغییرات محلی ثبت‌نشده را از بین ببرد.

اگر فایلی را ویرایش کرده باشی و تغییرات آن را commit نکرده باشی، اجرای این دستور ممکن است آن تغییرات را حذف کند.

همچنین تغییرات staged که هنوز commit نشده‌اند، ممکن است از دست بروند.

قبل از اجرا، وضعیت را بررسی کن:

```bash
git status
```

اگر تغییرات مهمی وجود دارد، ابتدا آن‌ها را commit یا stash کن، یا از فایل‌ها نسخهٔ پشتیبان بگیر.

### کاربردهای `hard`

این حالت در شرایطی کاربرد دارد که واقعاً بخواهی فایل‌های tracked را به وضعیت یک commit مشخص برگردانی؛ برای مثال:

- می‌خواهی تغییرات محلی tracked را کنار بگذاری.
- می‌خواهی یک شاخهٔ محلی را به وضعیت commit مشخصی برگردانی.
- پس از بررسی دقیق، تصمیم گرفته‌ای محتوای فعلی فایل‌های tracked دیگر لازم نیست.

### مثال

فرض کن تاریخچه چنین است:

```text
A --- B --- C  (HEAD -> main)
```

و می‌خواهی شاخه و فایل‌های tracked را به وضعیت `B` برگردانی:

```bash
git reset --hard B
```

پس از اجرا:

```text
A --- B  (HEAD -> main)
       \
        C
```

نکته: فایل‌های untracked معمولاً با `git reset --hard` حذف نمی‌شوند. حذف فایل‌های untracked موضوع جداگانه‌ای است و دستورهایی مانند `git clean` می‌توانند روی آن‌ها اثر بگذارند؛ بنابراین نباید این دو رفتار را با هم اشتباه گرفت.

# فصل چهارم: مقایسهٔ سه حالت

| ویژگی | `soft` | `mixed` | `hard` |
|---|---|---|---|
| جابه‌جایی شاخه به commit هدف | بله | بله | بله |
| بازنشانی `index` | خیر | بله | بله |
| بازنویسی فایل‌های tracked در `working tree` | خیر | خیر | بله |
| نگه‌داشتن تغییرات commit کنارگذاشته‌شده در `index` | بله | خیر | خیر |
| نگه‌داشتن تغییرات معمول فایل‌های tracked در `working tree` | بله | بله | خیر، وضعیت با هدف هماهنگ می‌شود |
| ریسک از دست رفتن تغییرات ثبت‌نشده | کم | کم | زیاد |

یک راه ساده برای به‌خاطر سپردن این تفاوت:

```text
--soft   = فقط شاخه
--mixed  = شاخه + index
--hard   = شاخه + index + فایل‌های tracked
```

این خلاصه مدل آموزشی است؛ در مخزن‌هایی با فایل‌های پیچیده، mergeهای حل‌نشده یا وضعیت‌های غیرمعمول، باید پیش از اجرا جزئیات را بررسی کرد.

# فصل پنجم: تعیین commit هدف

دستور `git reset` معمولاً به یک commit هدف نیاز دارد.

برای تعیین هدف می‌توان از شناسهٔ commit، نام شاخه یا عبارت‌های نسبی استفاده کرد.

## ۵.۱. استفاده از `HEAD`

عبارت `HEAD` به commit فعلی اشاره می‌کند.

```bash
git reset --soft HEAD
```

این دستور شاخه را به commit فعلی منتقل می‌کند. چون هدف همان commit فعلی است، معمولاً برای تغییر تاریخچه کاربردی ندارد؛ با این حال، در حالت‌های مختلف می‌تواند وضعیت `index` را تغییر دهد.

برای مثال:

```bash
git reset --mixed HEAD
```

می‌تواند تغییرات staged را از حالت staged خارج کند، بدون اینکه فایل‌های کاری tracked بازنویسی شوند.

## ۵.۲. استفاده از `HEAD~1`

عبارت `HEAD~1` به اولین والد commit فعلی اشاره می‌کند.

```bash
git reset --soft HEAD~1
```

یعنی شاخه را به یک commit قبل‌تر منتقل کن.

## ۵.۳. استفاده از `HEAD~2`

عبارت `HEAD~2` معمولاً به دومین والد در زنجیرهٔ نخستین والدها اشاره می‌کند.

```bash
git reset --mixed HEAD~2
```

اگر تاریخچه چنین باشد:

```text
A --- B --- C --- D  (HEAD -> main)
```

هدف `HEAD~2` برابر `B` خواهد بود.

## ۵.۴. استفاده از شناسهٔ commit

ابتدا تاریخچه را مشاهده کن:

```bash
git log --oneline --decorate
```

نمونه:

```text
d4e5f6a feat(api): add endpoint
c3d4e5f fix(parser): handle empty input
b2c3d4e feat(core): add parser
a1b2c3d docs: initialize project
```

حالا می‌توانی commit هدف را انتخاب کنی:

```bash
git reset --mixed b2c3d4e
```

به‌جای حدس‌زدن شناسه، آن را از خروجی Git بردار.

## ۵.۵. تفاوت `HEAD~n` و `HEAD^`

در تاریخچهٔ خطی معمولی، این دو عبارت برای یک والد یکسان نتیجهٔ مشابهی دارند:

```bash
HEAD~1
```

```bash
HEAD^
```

اما مفهوم آن‌ها دقیقاً یکسان نیست.

- `HEAD^` به والد اول commit اشاره می‌کند.
- `HEAD~2` یعنی دو بار حرکت به سمت والد اول.
- در merge commitها، `HEAD^2` به والد دوم اشاره می‌کند.

مثال:

```bash
git reset --soft HEAD^
```

این دستور شاخه را به والد اول commit فعلی منتقل می‌کند.

برای تاریخچه‌های دارای merge، باید با دقت بیشتری والد موردنظر را انتخاب کرد.

# فصل ششم: بازنشانی یک فایل

یکی از نکات مهم این است که `git reset` همیشه به معنای جابه‌جایی شاخه یا حذف commit نیست.

می‌توان از آن برای تغییر وضعیت یک فایل در `index` نیز استفاده کرد.

## ۶.۱. خارج‌کردن یک فایل از حالت staged

فرض کن این دستور را اجرا کرده‌ای:

```bash
git add app.py
```

حالا می‌خواهی فقط فایل `app.py` را از `staging area` خارج کنی.

```bash
git reset -- app.py
```

این دستور، نسخهٔ staged فایل را با نسخهٔ موجود در `HEAD` هماهنگ می‌کند، اما تغییرات موجود در `working tree` را نگه می‌دارد.

بنابراین اگر `app.py` را ویرایش کرده باشی، تغییرات آن معمولاً باقی می‌مانند؛ فقط دیگر staged نیستند.

این روش معادل رایج زیر است:

```bash
git restore --staged app.py
```

### چرا `--` مهم است؟

علامت `--` مرز میان گزینه‌های دستور و مسیر فایل‌ها را مشخص می‌کند.

این کار به Git می‌گوید که عبارت بعدی را به‌عنوان مسیر فایل تفسیر کند، نه گزینه یا نام revision.

## ۶.۲. خارج‌کردن چند فایل از حالت staged

```bash
git reset -- app.py README.md
```

در این مثال، هر دو فایل از حالت staged خارج می‌شوند؛ تغییرات معمول موجود در فایل‌های کاری باقی می‌مانند.

## ۶.۳. خارج‌کردن تمام فایل‌های staged

```bash
git reset
```

در حالت پیش‌فرض، این دستور `index` را با `HEAD` هماهنگ می‌کند و فایل‌های tracked را در `working tree` بازنویسی نمی‌کند.

بنابراین تغییرات staged از حالت staged خارج می‌شوند، اما تغییرات معمول فایل‌ها باقی می‌مانند.

## ۶.۴. تفاوت reset روی فایل و reset روی commit

این دو دستور رفتار متفاوتی دارند:

```bash
git reset -- app.py
```

```bash
git reset HEAD~1
```

دستور اول فقط وضعیت یک مسیر را در `index` تغییر می‌دهد و شاخه را جابه‌جا نمی‌کند.

دستور دوم شاخهٔ فعلی را به commit قبلی منتقل می‌کند و در حالت پیش‌فرض `index` را نیز بازنشانی می‌کند.

این تفاوت برای جلوگیری از اشتباه بسیار مهم است.

# فصل هفتم: تفاوت `git reset` و `git restore`

هر دو دستور می‌توانند در اصلاح وضعیت فایل‌ها مفید باشند، اما هدف و دامنهٔ اثر آن‌ها یکسان نیست.

## ۷.۱. خارج‌کردن فایل از حالت staged

روش قدیمی‌تر و همچنان معتبر:

```bash
git reset -- app.py
```

روش امروزی و صریح‌تر:

```bash
git restore --staged app.py
```

برای خارج‌کردن چند فایل:

```bash
git restore --staged app.py README.md
```

این دستورها تغییرات موجود در `working tree` را به‌طور معمول حفظ می‌کنند.

## ۷.۲. کنارگذاشتن تغییرات unstaged

اگر می‌خواهی تغییرات فایل tracked را در `working tree` با نسخهٔ موجود در `index` جایگزین کنی:

```bash
git restore app.py
```

این دستور ممکن است تغییرات ثبت‌نشدهٔ فایل را از بین ببرد.

اگر فایل staged و unstaged تغییرات متفاوتی داشته باشد، این دستور معمولاً فقط تغییرات unstaged را کنار می‌گذارد و محتوای staged را مبنا قرار می‌دهد.

برای بازگرداندن فایل به نسخهٔ موجود در `HEAD` می‌توانی صریح‌تر بنویسی:

```bash
git restore --source=HEAD --staged --worktree app.py
```

این دستور هم `index` و هم `working tree` فایل را با `HEAD` هماهنگ می‌کند؛ بنابراین باید پیش از اجرا، تغییرات مهم را بررسی کنی.

## ۷.۳. قاعدهٔ انتخاب

برای مدیریت فایل‌ها:

- از `git restore --staged` برای خارج‌کردن فایل از حالت staged استفاده کن.
- از `git restore` برای بازگرداندن فایل کاری به نسخهٔ مبنا استفاده کن.
- از `git reset <target>` برای جابه‌جایی شاخه به commit هدف استفاده کن.

این قاعده مطلق نیست، اما برای بسیاری از کارهای روزمره انتخاب مناسبی است.

# فصل هشتم: تفاوت `git reset` و `git revert`

این دو دستور اغلب با هم اشتباه گرفته می‌شوند.

## ۸.۱. رفتار `git reset`

دستور `git reset` می‌تواند محل اشارهٔ شاخه را تغییر دهد و commitهای بعد از هدف را از تاریخچهٔ شاخه کنار بگذارد.

مثال:

```bash
git reset --hard HEAD~1
```

این دستور شاخه را به commit قبلی منتقل می‌کند و فایل‌های tracked را با آن هماهنگ می‌کند.

## ۸.۲. رفتار `git revert`

دستور `git revert` برای خنثی‌کردن اثر یک commit با ساختن commit جدید استفاده می‌شود.

مثال:

```bash
git revert HEAD
```

در حالت عادی، Git یک commit جدید ایجاد می‌کند که تغییرات commit هدف را معکوس می‌کند.

تاریخچه ممکن است به این شکل باشد:

```text
A --- B --- C --- D
```

اگر `C` را revert کنیم، تاریخچه همچنان commitهای قبلی را حفظ می‌کند و یک commit جدید برای خنثی‌کردن تغییرات `C` اضافه می‌شود.

## ۸.۳. چه زمانی کدام را انتخاب کنیم؟

اگر commit هنوز فقط در شاخهٔ محلی توست و می‌خواهی تاریخچه را بازنویسی کنی، `reset` ممکن است مناسب باشد.

اگر commit به شاخهٔ مشترک push شده است و می‌خواهی اثر آن را با حفظ تاریخچه خنثی کنی، معمولاً `revert` انتخاب امن‌تری است.

نکته: `git revert` در برخی شرایط، به‌ویژه هنگام revert کردن merge commit، به انتخاب والد و بررسی اثر تغییرات نیاز دارد.

# فصل نهم: کاربردهای واقعی `git reset`

## ۹.۱. اصلاح پیام آخرین commit

اگر هنوز commit را push نکرده‌ای، روش معمول برای اصلاح پیام آخرین commit چنین است:

```bash
git commit --amend -m "feat(api): validate request input"
```

در بسیاری از موارد، این روش از اجرای `reset` ساده‌تر است.

روش جایگزین:

```bash
git reset --soft HEAD~1
git commit -m "feat(api): validate request input"
```

هر دو روش می‌توانند commit جدیدی با پیام جدید بسازند، اما `amend` برای اصلاح آخرین commit صریح‌تر است.

## ۹.۲. تبدیل چند commit به یک commit

فرض کن سه commit محلی داری:

```text
A --- B --- C --- D  (HEAD -> feature/parser)
```

می‌خواهی تغییرات سه commit آخر را در یک commit جمع کنی.

```bash
git reset --soft HEAD~3
```

اکنون شاخه به `A` منتقل می‌شود و تغییرات سه commit اخیر در `index` باقی می‌مانند.

سپس:

```bash
git commit -m "feat(parser): add parser implementation"
```

نتیجه، یک commit جدید با محتوای ترکیبی خواهد بود.

این روش زمانی مناسب است که بخواهی commitهای محلی و هنوز منتشرنشده را ساده‌تر کنی.

## ۹.۳. کنارگذاشتن commit اشتباه، با حفظ تغییرات

فرض کن آخرین commit اشتباهی ساخته شده و می‌خواهی محتوای آن را دوباره بررسی کنی.

```bash
git reset --mixed HEAD~1
```

اکنون تغییرات معمولاً در فایل‌های کاری باقی می‌مانند، اما دیگر staged نیستند.

می‌توانی آن‌ها را بررسی کنی:

```bash
git diff
```

سپس فقط فایل‌های موردنیاز را stage کنی:

```bash
git add app.py
git commit -m "fix(app): handle invalid input"
```

## ۹.۴. بازگشت شاخه به commit مشخص

ابتدا تاریخچه را ببین:

```bash
git log --oneline --decorate
```

سپس commit هدف را انتخاب کن:

```bash
git reset --mixed <commit-id>
```

اگر می‌خواهی فایل‌های tracked نیز با وضعیت هدف هماهنگ شوند، می‌توانی از `hard` استفاده کنی؛ اما این کار تغییرات ثبت‌نشده را به خطر می‌اندازد.

## ۹.۵. حذف اشتباهی فایل از حالت staged

اگر اشتباهاً همهٔ فایل‌ها را stage کرده‌ای:

```bash
git add .
```

می‌توانی همه را از حالت staged خارج کنی:

```bash
git reset
```

سپس فایل‌های موردنیاز را جداگانه اضافه کن:

```bash
git add src/app.py
git add tests/test_app.py
```

این روش کمک می‌کند از ثبت فایل‌های نامرتبط در commit جلوگیری کنی.

# فصل دهم: رفتار `reset` در مخزن‌های دارای merge

تاریخچهٔ Git همیشه خطی نیست.

فرض کن شاخه‌ای پس از merge به شکل زیر درآمده است:

```text
       C --- D
      /       \
A --- B ------- M  (HEAD -> main)
```

در این مثال، `M` یک merge commit است.

وقتی می‌نویسی:

```bash
git reset HEAD~1
```

هدف `HEAD~1` معمولاً والد اول merge commit است، نه لزوماً آخرین commitی که از شاخهٔ ادغام‌شده وارد شده است.

برای مشاهدهٔ والدهای merge commit:

```bash
git show --no-patch --pretty=raw HEAD
```

برای بررسی تاریخچهٔ گرافی:

```bash
git log --oneline --graph --decorate --all
```

در تاریخچه‌های دارای merge، قبل از استفاده از `reset` باید دقیقاً مشخص کنی کدام commit هدف است.

# فصل یازدهم: بازیابی پس از `reset`

یکی از مهم‌ترین مهارت‌های کار با Git، دانستن روش بازیابی بعد از اشتباه است.

## ۱۱.۱. چرا بعضی commitها پس از reset قابل‌بازیابی‌اند؟

اصلاحیه: Git معمولاً commitها را به‌صورت object ذخیره می‌کند. جابه‌جایی شاخه با `reset` به این معنا نیست که commit قدیمی بلافاصله از دیسک پاک می‌شود.

اگر commit دیگر از طریق شاخه یا reference دیگری قابل‌دسترسی نباشد، ممکن است مدتی از طریق سابقهٔ محلی `reflog` یا با ابزارهای دیگر قابل‌بازیابی بماند.

با این حال، نباید روی ماندگاری همیشگی آن حساب کرد. Git می‌تواند objectهای غیرقابل‌دسترسی را پس از گذشت زمان و اجرای عملیات پاک‌سازی حذف کند.

## ۱۱.۲. مشاهدهٔ `reflog`

برای دیدن سابقهٔ جابه‌جایی‌های `HEAD`:

```bash
git reflog
```

نمونهٔ فرضی:

```text
f6e7d8a HEAD@{0}: reset: moving to HEAD~1
a5b6c7d HEAD@{1}: commit: feat(api): add endpoint
9a8b7c6 HEAD@{2}: commit: docs: add API guide
```

در این مثال، commit `a5b6c7d` ممکن است همان commitی باشد که قبل از reset در رأس شاخه قرار داشت.

## ۱۱.۳. بازیابی شاخه

اگر مطمئن شدی که commit موردنظر همان `a5b6c7d` است، می‌توانی شاخه را به آن برگردانی:

```bash
git reset --hard a5b6c7d
```

این دستور شاخه را به commit مشخص‌شده منتقل می‌کند و فایل‌های tracked را نیز با آن هماهنگ می‌سازد.

هشدار: اگر پس از reset تغییرات جدیدی ایجاد کرده‌ای، این دستور می‌تواند آن‌ها را از بین ببرد. ابتدا وضعیت مخزن را بررسی کن و اگر لازم است از تغییرات فعلی نسخهٔ پشتیبان بگیر.

اگر فقط می‌خواهی commit را بدون تغییر شاخه بررسی کنی:

```bash
git show a5b6c7d
```

همچنین می‌توانی یک شاخهٔ بازیابی بسازی:

```bash
git branch recovery/before-reset a5b6c7d
```

این روش معمولاً برای محافظت از commit بازیابی‌شده مناسب‌تر است؛ زیرا یک reference جدید به آن ایجاد می‌کند.

## ۱۱.۴. محدودیت `reflog`

اصلاحیه: `reflog` سابقهٔ محلی تغییر referenceها را ثبت می‌کند، اما یک نسخهٔ پشتیبان دائمی نیست.

ممکن است در شرایطی مانند پاک‌سازی objectها، حذف اطلاعات محلی یا کار در مخزن دیگری نتوانی به commit موردنظر دسترسی پیدا کنی.

برای تغییرات مهم، بهترین کار این است که پیش از عملیات حساس یک شاخهٔ پشتیبان بسازی:

```bash
git branch backup/before-reset
```

این دستور شاخه‌ای با نام `backup/before-reset` ایجاد می‌کند که به commit فعلی اشاره دارد.

# فصل دوازدهم: اشتباهات رایج

## ۱۲.۱. اجرای `--hard` بدون بررسی وضعیت

دستور زیر ممکن است تغییرات مهم را از بین ببرد:

```bash
git reset --hard HEAD~1
```

قبل از اجرا:

```bash
git status
git diff
git diff --cached
```

اگر تغییرات مهمی داری، آن‌ها را commit یا stash کن یا نسخهٔ پشتیبان بگیر.

## ۱۲.۲. تصور اینکه `reset` همه‌چیز را پاک می‌کند

دستور `git reset --hard` فایل‌های tracked را با commit هدف هماهنگ می‌کند؛ اما به‌طور معمول فایل‌های untracked را حذف نمی‌کند.

برای بررسی فایل‌های untracked:

```bash
git status --short
```

دستور `git clean` می‌تواند فایل‌های untracked را حذف کند و باید جداگانه و با دقت استفاده شود.

## ۱۲.۳. استفاده از `reset` روی commitهای منتشرشده

اگر commitها قبلاً push شده‌اند، بازنویسی تاریخچه ممکن است باعث اختلاف میان تاریخچهٔ محلی و remote شود.

در مخزن مشترک، برای خنثی‌کردن یک commit منتشرشده معمولاً `git revert` مناسب‌تر است.

## ۱۲.۴. اشتباه‌گرفتن `git reset` با حذف دائمی commit

جابجایی شاخه به این معنا نیست که commit هدف‌نبوده فوراً از دیسک حذف می‌شود.

اگر commit دیگری به آن اشاره نکند، ممکن است همچنان از طریق `reflog` یا تا زمان پاک‌سازی objectها قابل‌بازیابی باشد.

## ۱۲.۵. نادیده‌گرفتن فایل‌های staged و unstaged

یک فایل ممکن است هم‌زمان تغییرات staged و unstaged داشته باشد.

برای بررسی آن‌ها:

```bash
git diff --cached
git diff
```

این دو دستور بخش‌های متفاوتی از تغییرات را نمایش می‌دهند.

# فصل سیزدهم: راهنمای انتخاب دستور

| هدف | دستور پیشنهادی |
|---|---|
| بازکردن آخرین commit و نگه‌داشتن تغییرات در حالت staged | `git reset --soft HEAD~1` |
| بازکردن آخرین commit و خارج‌کردن تغییرات از حالت staged | `git reset --mixed HEAD~1` |
| بازگرداندن شاخه و فایل‌های tracked به commit قبلی | `git reset --hard HEAD~1` |
| خارج‌کردن یک فایل از حالت staged | `git restore --staged app.py` |
| کنارگذاشتن تغییرات unstaged یک فایل tracked | `git restore app.py` |
| خنثی‌کردن یک commit منتشرشده با حفظ تاریخچه | `git revert <commit>` |
| مشاهدهٔ سابقهٔ جابه‌جایی‌های `HEAD` | `git reflog` |
| بررسی تاریخچهٔ شاخه | `git log --oneline --graph --decorate --all` |
| ایجاد شاخهٔ پشتیبان قبل از عملیات حساس | `git branch backup/before-reset` |

# فصل چهاردهم: تمرین‌های عملی

این تمرین‌ها را ابتدا در یک مخزن آزمایشی انجام بده، نه در مخزن اصلی پروژه.

## تمرین ۱: ساخت مخزن آزمایشی

```bash
mkdir reset-lab
cd reset-lab
git init
```

اگر Git نام شاخهٔ پیش‌فرض را تعیین نکرده یا می‌خواهی نام آن `main` باشد:

```bash
git branch -M main
```

یک فایل ایجاد کن:

```bash
printf "version 1\n" > app.txt
git add app.txt
git commit -m "chore: add initial file"
```

## تمرین ۲: ساخت commit دوم

```bash
printf "version 2\n" >> app.txt
git add app.txt
git commit -m "feat: add second version"
```

تاریخچه را بررسی کن:

```bash
git log --oneline --decorate
```

## تمرین ۳: آزمایش `--soft`

```bash
git reset --soft HEAD~1
git status
git diff --cached
```

مشاهده کن که تغییرات commit دوم در `index` باقی مانده‌اند.

سپس commit را دوباره بساز:

```bash
git commit -m "feat: add second version again"
```

## تمرین ۴: آزمایش `--mixed`

```bash
git reset --mixed HEAD~1
git status
git diff
```

مشاهده کن که تغییرات فایل در `working tree` باقی مانده‌اند، اما staged نیستند.

حالا commit را دوباره بساز:

```bash
git add app.txt
git commit -m "feat: add second version"
```

## تمرین ۵: آزمایش reset روی فایل

ابتدا فایل را تغییر بده:

```bash
printf "version 3\n" >> app.txt
git add app.txt
```

حالا فایل را از حالت staged خارج کن:

```bash
git restore --staged app.txt
```

وضعیت را بررسی کن:

```bash
git status
git diff
```

تغییرات فایل باید باقی مانده باشند، اما staged نباشند.

## تمرین ۶: آزمایش بازیابی با `reflog`

ابتدا تاریخچه را مشاهده کن:

```bash
git log --oneline --decorate
```

یک commit جدید بساز:

```bash
printf "version 4\n" >> app.txt
git add app.txt
git commit -m "feat: add fourth version"
```

حالا یک reset انجام بده:

```bash
git reset --hard HEAD~1
```

تاریخچه و `reflog` را بررسی کن:

```bash
git log --oneline --decorate
git reflog
```

شناسهٔ commit حذف‌شده از رأس شاخه را پیدا کن. برای بازیابی امن‌تر، یک شاخهٔ جدید بساز:

```bash
git branch recovery/test-reset <commit-id>
```

به‌جای `<commit-id>` شناسهٔ واقعی commit را وارد کن.

سپس شاخهٔ بازیابی را بررسی کن:

```bash
git log --oneline recovery/test-reset
```

این تمرین نشان می‌دهد که کنارگذاشتن یک commit از رأس شاخه الزاماً به معنی حذف فوری object آن نیست.

# فصل پانزدهم: خلاصهٔ نهایی

دستور `git reset` ابزار قدرتمندی برای تغییر وضعیت شاخه و `index` است. انتخاب حالت مناسب به این بستگی دارد که کدام بخش از وضعیت Git را می‌خواهی حفظ کنی.

```bash
# Move the current branch while keeping the index and working tree.
git reset --soft HEAD~1

# Move the current branch and reset the index.
# This is the default reset mode.
git reset --mixed HEAD~1

# Move the current branch, reset the index,
# and update tracked working-tree files.
git reset --hard HEAD~1

# Unstage one file without discarding its working-tree changes.
git restore --staged app.py

# Discard unstaged changes in one tracked file.
git restore app.py

# Inspect local reference history.
git reflog

# Create a safety branch before a risky operation.
git branch backup/before-reset
```

## قواعدی که باید به خاطر بسپاری

۱. حالت `--soft` برای بازکردن commit و نگه‌داشتن تغییرات در حالت staged مناسب است.

۲. حالت `--mixed` برای بازکردن commit و خارج‌کردن تغییرات از حالت staged مناسب است.

۳. حالت `--hard` علاوه بر جابه‌جایی شاخه، فایل‌های tracked را نیز با وضعیت هدف هماهنگ می‌کند و می‌تواند تغییرات ثبت‌نشده را از بین ببرد.

۴. دستور `git reset -- <file>` برای بازنشانی وضعیت یک مسیر در `index` استفاده می‌شود و با reset کردن شاخه تفاوت دارد.

۵. برای مدیریت روزمرهٔ فایل‌ها، دستورهای `git restore` معمولاً قصد تو را واضح‌تر بیان می‌کنند.

۶. برای خنثی‌کردن تغییرات commitهای منتشرشده در مخزن مشترک، معمولاً `git revert` مناسب‌تر است.

۷. پیش از عملیات حساس، وضعیت مخزن را بررسی کن و در صورت نیاز یک شاخهٔ پشتیبان بساز.

۸. دستور `git reflog` می‌تواند برای بازیابی commitهایی که به‌تازگی از رأس شاخه کنار گذاشته شده‌اند مفید باشد، اما جایگزین نسخهٔ پشتیبان نیست.

**مهم‌ترین اصل:** پیش از اجرای `git reset`، دقیقاً مشخص کن که می‌خواهی شاخه، `index` یا فایل‌های کاری تغییر کنند. هرچه دامنهٔ بازنشانی بیشتر باشد، احتمال از دست‌دادن تغییرات نیز بیشتر می‌شود.
